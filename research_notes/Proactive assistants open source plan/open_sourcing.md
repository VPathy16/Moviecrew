# Open-sourcing "Boop" (Kotlin/Compose Android AI assistant): licensing, distribution, security, naming, contribution model, sustainability, privacy — state as of late October 2026

Research notes compiled 2026-10-24 to 2026-10-26. Licence metadata for dependencies and reference repos came from Maven POMs, deps.dev and GitHub metadata (via the ecosyste.ms API). The GitHub API was not reachable from this session. Star counts and "last pushed" dates are as of 2026-10-24.

## 1. Licence choice for the app (Apache-2.0 vs MIT vs GPL-3.0 vs AGPL-3.0 vs MPL-2.0), dependency compatibility, and what similar projects chose

### Takeaway
Every library in Boop's stack except ML Kit GenAI is permissive (Apache-2.0 or MIT), or, for JavaMail, dual or tri-licensed in a way that lets you pick a non-GPL option. Apache-2.0 is the lowest-friction choice and adds an explicit patent grant. GPL-3.0 or AGPL-3.0 for the app is legally workable only if you, as copyright holder, add a linking exception for the proprietary ML Kit/Play-services pieces, or move them into a separate flavour. Among reference projects, the permissive camp (OpenClaw MIT, Home Assistant Apache-2.0, Thunderbird for Android Apache-2.0, Jan Apache-2.0, Leon MIT, Google AI Edge Gallery Apache-2.0) is larger and better-funded than the copyleft camp (Signal AGPL-3.0, NewPipe GPL-3.0, RikkaHub/ChatterUI AGPL-3.0). Open WebUI shows a licence that stopped being OSI open source when the maintainers added a branding clause.

**Compatibility rules**
- ASF: "Apache 2 software can therefore be included in GPLv3 projects", but "GPLv3 software cannot be included in Apache projects". The licences are "incompatible in one direction only", and "the FSF has never considered the Apache License to be compatible with GPL version 2", citing the patent termination and indemnification clauses — [Apache GPL compatibility](https://www.apache.org/licenses/GPL-compatibility.html)
- GNU FAQ: "If you want your program to link against a library not covered by the system library exception, you need to provide permission to do that… Only the copyright holders for the program can legally release their software under these terms." Under GPLv3 this is done "by granting an additional permission under section 7". Later contributors "do not have to make the same exception for their code" — [GPL FAQ #GPLIncompatibleLibs](https://www.gnu.org/licenses/gpl-faq.html#GPLIncompatibleLibs)
- GNU FAQ on non-free libraries: "If it depends on a nonfree library to run at all, it cannot be part of a free operating system". If the program already uses one, "mention in the README that the need for the nonfree library is a drawback" — [GPL FAQ #FSWithNFLibs](https://www.gnu.org/licenses/gpl-faq.html#FSWithNFLibs)

### Inferences
- **Recommended default: Apache-2.0.** It matches most of the dependency tree (OkHttp, Tink, kotlinx.serialization, androidx, anthropic-java, openai-java). It gives an explicit patent grant with defensive termination, which matters for a project that may later attract corporate contributors. It is also what Home Assistant, Thunderbird for Android, Jan and Google's own Edge Gallery use. MIT is close behind, but it has no patent grant and no NOTICE mechanism.
- **JavaMail:** ship android-mail under its EPL-2.0 option, not GPL-2.0+CE. EPL-2.0 is weak, file-level copyleft: modified EPL files must stay EPL and their source must be available. Using it unmodified as a separate jar inside an Apache-2.0 app is the common pattern. I could not retrieve the Eclipse EPL-2.0 FAQ to quote it (see Gaps). Because android-mail 1.6.8 is the final com.sun.mail build, consider Angus Mail or dropping SMTP/IMAP in favour of the Gmail MCP/API.
- **GPL-3.0/AGPL-3.0 would only make sense** if the goal is to stop closed-source rebrands; RikkaHub and ChatterUI chose AGPL for this reason. The cost is that you must write a GPLv3 §7 additional permission for ML Kit/Play services (per the GNU FAQ). Contributors' later code need not carry that exception, which can cause trouble down the line. AGPL's network clause adds little to a client-side Android app.
- **MPL-2.0** is a reasonable middle ground if you want file-level copyleft without the GPL linking issues. No reference project in this niche uses it.
- **Avoid an Open-WebUI-style branding clause.** It cost that project OSI status and would block F-Droid inclusion, which requires FLOSS. Protect the name with trademark policy instead (see section 4).
- Put the proprietary ML Kit GenAI/Gemini Nano dependency only in a `play` (or `gms`) product flavour. That keeps the `foss` flavour fully FLOSS and makes the licence question moot for F-Droid.

### Gaps
- Could not fetch the Eclipse EPL-2.0 FAQ (page returned navigation only), so EPL-2.0 + Apache-2.0 combination rules are inferred, not quoted.
- Did not retrieve the text of the "ML Kit GenAI API Additional Terms of Service". Any redistribution limits or use restrictions (for example, a generative-AI prohibited-use policy) beyond the main ML Kit Terms are unverified.
- Did not verify each transitive dependency, such as the Compose BOM, Ktor if pulled in by the MCP SDK, or Gemini Live client code. Run a licence report (for example, the Gradle licensee/licence-report plugins) before release.
- OpenClaw, Leon, Signal etc. did not publish rationales for their licence choice that I could find. The only explicit rationales found are Jan's (AGPL→Apache, adoption) and Open WebUI's (branding/sustainability).

## 2. Distribution: Google Play policy, developer verification, F-Droid, IzzyOnDroid, GitHub releases, flavours

### Takeaway
Since early 2026 Google Play policy prohibits using the Accessibility API so that an app can "autonomously initiate, plan, and execute actions". Boop's optional accessibility-driven actions therefore cannot ship in the Play build. Read-only screen context needs a prominent in-app disclosure, a declaration form and a demo video. On Play, Boop is also in scope of the AI-Generated Content policy (in-app reporting required), the Financial features declaration (required for every app), and Data safety. Off Play, Android developer verification began enforcement on 30 Sep 2026 in Brazil, Indonesia, Singapore and Thailand, with a global rollout planned for 2027; F-Droid opposes it. F-Droid requires 100% FLOSS, so ML Kit/Play services must be in a separate flavour, and cloud-LLM dependence will likely earn a NonFreeNet anti-feature. IzzyOnDroid is a faster path: it uses upstream-built APKs, allows no trackers, and prefers reproducible builds.

### Cited Findings

**Google Play — Accessibility API**
- Policy text: "Any use of the Accessibility API that enables an app to autonomously initiate, plan, and execute actions" is prohibited. "Deterministic, rule-based automation" where "behavior follows a static, human-defined script" is not prohibited. Only services "designed to help people with disabilities" may declare `isAccessibilityTool`, and a general voice assistant does not qualify — [Play: Use of the AccessibilityService API](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)
- Apps that are not accessibility tools need an in-app prominent disclosure that "cannot only be in the app description or on a website", plus affirmative consent, a Play Console declaration, and a video showing the disclosure, the consent and non-consent flows, and a core feature using the API — [same page](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)
- A secondary source dates the autonomy restriction to 28 January 2026 and lists LLM agents that "book, buy, message, or change settings" via accessibility as prohibited. It describes AppFunctions, MCP/app APIs and Gemini in-app tasks as the sanctioned alternatives — [OpenAlly blog](https://openally.ai/blog/how-ai-agents-do-things-on-your-phone); [dev.to five routes in 2026](https://dev.to/alon_n_ecceca6aa868e0761d/how-an-ai-agent-can-use-android-apps-that-have-no-api-five-routes-in-2026-2gfe) (secondary; the effective date is not confirmed on Google's page)
- Platform side: in Android 17.2, with Advanced Protection Mode enabled, the system blocks non-accessibility apps from using accessibility services. Malwarebytes reports that "password managers or automation apps aren't getting to the accessibility API anymore" (17 March 2026) — [Malwarebytes](https://www.malwarebytes.com/blog/mobile/2026/03/google-cracks-down-on-android-apps-abusing-accessibility)

**Google Play — other policies relevant to Boop**
- **AI-Generated Content policy:** in scope are "Text-to-text conversational generative AI chatbots, in which interacting with the chatbot is a central feature of the app". Apps must "contain in-app user reporting or flagging features that allow users to report or flag offensive content" — [Play AI-Generated Content](https://support.google.com/googleplay/android-developer/answer/13985936?hl=en); [Play AI content examples page](https://support.google.com/googleplay/android-developer/answer/14094294?hl=en). Summarisation-only apps and productivity apps that add AI to an existing feature are out of scope (same page).
- **15 July 2026 policy announcement:** (a) a clarification that User Data policy requirements "also apply to third-party AI integrations", with developers responsible for limited use, disclosure and consent; (b) apps must be registered in Play Console for Android developer verification, or face "global removal from Google Play"; (c) target-API deadline of 31 August 2026; (d) new chat-app child-safety rules for anonymous/random chat; (e) an open-source "Android skill" that grounds LLMs in Play policies for code review — [Play policy announcement 15 July 2026](https://support.google.com/googleplay/android-developer/answer/17134731?hl=en-GB)
- **Permissions policy:** SMS and Call Log permissions require being the default SMS, Phone **or Assistant** handler plus a declaration form, and the app must "immediately stop using the permission" once it loses default status. The policy page does not address the launcher/home role or NotificationListenerService. Declaration forms are required for QUERY_ALL_PACKAGES, MANAGE_EXTERNAL_STORAGE, background location, REQUEST_INSTALL_PACKAGES, USE_FULL_SCREEN_INTENT, USE_EXACT_ALARM and AccessibilityService — [Play: Permissions and APIs that Access Sensitive Information](https://support.google.com/googleplay/android-developer/answer/9888170?hl=en)
- **Financial features declaration:** mandatory for every published app since 31 Aug 2023: "Even developers with apps that do not offer any financial features must complete this form". Categories include "Mobile payments and digital wallets" and "Stock trading and portfolio management". The page does not say whether UPI deep links or a broker API integration (Zerodha Kite) count as "providing" a financial feature — [Play: Financial features declaration](https://support.google.com/googleplay/android-developer/answer/13849271?hl=en)
- **Notification listener:** since Android 15, notifications that Android System Intelligence classifies as sensitive (for example OTPs) are hidden from "untrusted" listeners, which see "sensitive notification content hidden". The `RECEIVE_SENSITIVE_NOTIFICATIONS` permission is role|signature only — [Android Authority](https://www.androidauthority.com/android-15-sensitive-notifications-3416414); [KDE Connect MR](https://invent.kde.org/network/kdeconnect-android/-/merge_requests/492)

**Android developer verification (affects sideloading, F-Droid, GitHub releases)**
- Timeline: "August 2026: Developer APIs, limited distribution accounts, and power user advanced flow launch". From 30 September 2026, "Protections begin for all users who install apps from participating stores in Brazil, Indonesia, Singapore, and Thailand on certified devices running Android 7+". "Verification capability will be expanded globally for all apps on certified Android devices in 2027" — [developer.android.com/developer-verification](https://developer.android.com/developer-verification)
- Limited distribution accounts let "students, teachers, and hobbyists… share apps with up to 20 devices without a government-issued ID or registration fee". Google has a guide for registering open-source apps ("Register an app on open-source registry"). Play "automatically registers 99% of apps" — [same page](https://developer.android.com/developer-verification)
- Advanced flow, per secondary reporting: the user enables Developer Mode, waits 24 hours, re-authenticates, then may allow unverified installs for 7 days or indefinitely — [Gadget Hacks](https://android.gadgethacks.com/news/google-android-sideloading-restrictions-sept-30-explained/)
- F-Droid's February 2026 open letter calls mandatory registration a threat to community repositories and direct downloads, and F-Droid advises developers not to sign up — [F-Droid open letter, 24 Feb 2026](https://f-droid.org/ca/2026/02/24/open-letter-opposing-developer-verification.html). A third-party blog reports F-Droid 2.0 (a client rewrite) released 24 Sept 2026 — [Pinggy blog](https://pinggy.io/blog/f_droid_2_0_android_developer_verification/) (secondary)

**F-Droid**
- "All applications in the repository must be Free, Libre and Open Source Software (FLOSS)". Proprietary tracking/analytics "such as Google Play Services and Firebase" are banned, and upstream must offer a FLOSS build flavour without them. The build needs "a 100% FLOSS toolchain", dependencies must come from source or trusted Maven repos (Maven Central, Google Maven), and downloading executable code requires explicit opt-in — [F-Droid Inclusion Policy](https://f-droid.org/docs/Inclusion_Policy/)
- Anti-features: **NonFreeNet** = "apps that promote or depend entirely on a proprietary network service". **NonFreeDep** = "require things that are not Free Software in order to run". **TetheredNet** does not apply if there is "a simple configuration option that allows pointing the app to a running instance" of a self-hostable alternative. **Tracking** = reporting activity "without your permission or by default". "Undisclosed anti-features will receive a rejection" — [F-Droid Anti-Features](https://f-droid.org/docs/Anti-Features/); [Inclusion Policy](https://f-droid.org/docs/Inclusion_Policy/)
- Reproducible builds: F-Droid can publish **APKs signed with the developer's own key**. It rebuilds, copies the upstream signature and checks it verifies (`Binaries:` and `AllowedAPKSigningKeys:` metadata); "F-Droid will never attempt to publish APKs signed by F-Droid" in that mode. Pitfalls: embedded timestamps ("the most common source"), mixed JDKs, non-deterministic `baseline.prof`, some R8 optimisations, and build-tools ≥35.0.0-rc1 apksigner output that apksigcopier cannot verify (use build-tools 34) — [F-Droid Reproducible Builds](https://f-droid.org/docs/Reproducible_Builds/)

**IzzyOnDroid**
- Requires an OSI/FSF-approved licence and accessible source, and allows no trackers (ads or analytics). It prefers APKs attached to tagged releases, which makes reproducible builds possible. It sets a roughly 30 MB per-APK limit. It does not build apps itself and uses rbtlog-based verification builders; about 18% of apps were reproducible at the time of that post — [IzzyOnDroid inclusion policy](https://izzyondroid.org/docs/general/AppInclusionPolicy/); [IzzyOnDroid Reproducible Builds](https://izzyondroid.org/about/security/ReproducibleBuilds/); [FOSDEM 2026 RB slides](https://fosdem.org/2026/events/attachments/8VDKQR-reproducible_builds_for_android_apps/slides/262296/reproduci_6aivegw.pdf)
- Its FAQ says cross-updates from F-Droid are not possible unless the app is reproducible — [IzzyOnDroid FAQ](https://izzyondroid.org/faq/)

**Precedent for "open source plus Play-specific config"**
- Thunderbird for Android ships Apache-2.0 source with per-flavour OAuth configs (debug, daily, beta, release) and is distributed on both Play and F-Droid — [README](https://raw.githubusercontent.com/thunderbird/thunderbird-android/main/README.md); [F-Droid listing](https://f-droid.org/app/net.thunderbird.android)

### Inferences
- **Proposed flavour split:**
  - `play`: ML Kit GenAI/Gemini Nano; no accessibility *actions* (read-only screen context only, with disclosure and declaration, or omit it); AI-content report button; Play Integrity optional.
  - `foss`: no ML Kit or Play services; on-device fallback via an open runtime such as llama.cpp or MediaPipe, if its licence fits, or cloud-only; accessibility actions behind explicit opt-in; distributed via GitHub Releases, IzzyOnDroid and then F-Droid.
  - Same `applicationId` only if the signing key is the same; otherwise use different IDs to avoid update conflicts.
- Expect F-Droid to tag the app **NonFreeNet**, because Claude, OpenAI, Gemini, OpenRouter and the Swiggy, Zomato, Kite and Composio MCPs are proprietary services. Supporting any OpenAI-compatible base URL (Ollama, LM Studio, self-hosted) is the main argument against "depends entirely" and against TetheredNet.
- On Play, Boop needs: an accessibility declaration (if kept); the Financial features declaration (UPI → likely "Mobile payments"; Kite trading tools → likely "Stock trading and portfolio management", or a narrow "Other" answer; confirm with Play support); the Data safety form; an AI-content in-app reporting UI; and Gmail OAuth verification if the Play build ships its own Google client (see section 3).
- The default-Assistant role makes Boop *eligible* to request SMS/Call Log permissions, which brings heavy declaration review. Don't request them unless they're core.
- Given developer verification, register the package name and signing key in the Android Developer Console even for GitHub/IzzyOnDroid builds before the 2027 global rollout. Otherwise users on certified devices will face the advanced flow. This conflicts with F-Droid's advice, so the maintainer has to make a values call.
- Obtainium users can track GitHub Releases directly. Attach signed APKs (plus attestations) to tags, which also satisfies IzzyOnDroid's preference.

### Gaps
- Google's own announcement and effective date for the autonomy clause in the Accessibility policy were not retrieved; only secondary sources give 28 Jan 2026. The policy page I read contains the clause but no date.
- No Play policy text was found on the HOME/launcher role, NotificationListenerService, or UPI intent deep links for real-world goods. Play's Payments policy (physical goods exemption) was not fetched.
- Registration fees and key/package-name details for developer verification were not retrieved. The "open-source registry" guide was linked but not read.
- F-Droid has not ruled on Boop specifically. Whether a BYOK multi-provider client gets NonFreeNet is an inference from the definitions; check F-Droid listings of similar apps (for example GPT Mobile or RikkaHub, if listed).
- Obtainium documentation was not researched.

## 3. Secrets and security: OAuth client IDs, BYOK, SECURITY.md/disclosure, supply chain, prompt-injection hardening, OpenClaw lessons

### Takeaway
Installed and Android apps are public OAuth clients. Their client IDs are not secrets, and mature open-source mail apps (Thunderbird for Android) commit them in source but tell forks to register their own clients and use different redirect URIs. The real cost is Google's restricted-scope regime. Gmail scopes are "restricted", so a Play-distributed build with its own Google client needs verification plus an annual CASA security assessment. A "bring your own OAuth client" option for under-100-user personal use avoids this. For agent safety the consensus is architectural: avoid the "lethal trifecta" and treat external content as untrusted. OWASP's 2026 agentic list puts goal hijack first. OpenClaw's 2026 incidents (a one-click RCE CVE, a malware-laden skill registry, tens of thousands of exposed instances) show what an untrusted plugin ecosystem plus open network surfaces leads to.

### Cited Findings

**OAuth client IDs and secrets in open-source Android apps**
- Thunderbird for Android commits OAuth client IDs for Gmail, Microsoft, Yahoo, AOL and Fastmail in `TbOAuthConfigurationFactory.kt`. The Gmail entry uses scope `https://mail.google.com/` and redirect URI `${APPLICATION_ID}:/oauth2redirect`, with no client secret — [TbOAuthConfigurationFactory.kt (release)](https://raw.githubusercontent.com/thunderbird/thunderbird-android/main/app-thunderbird/src/release/kotlin/net/thunderbird/android/auth/TbOAuthConfigurationFactory.kt)
- Thunderbird README: forks must "replace the OAuth client setup in… K9OAuthConfigurationFactory.kt and… TbOAuthConfigurationFactory.kt with your own OAuth client setup and ensure that the `redirectUri` is different to the one used in the main project", to avoid conflicts when both apps are installed — [README](https://raw.githubusercontent.com/thunderbird/thunderbird-android/main/README.md)
- Google: desktop apps "are public clients and cannot keep secrets confidential". `client_secret` "is not applicable to requests from clients registered as Android, iOS, or Chrome applications". "Always use PKCE"; custom URI schemes "are no longer supported due to the risk of app impersonation" for some client types — [Google OAuth 2.0 for installed apps](https://developers.google.com/identity/protocols/oauth2/native-app)
- Gmail restricted scopes include `https://mail.google.com/` ("includes any usage of IMAP, SMTP, and POP3 protocols"), `gmail.readonly`, `gmail.modify` and `gmail.metadata` — [Google Cloud: restricted scopes](https://support.google.com/cloud/answer/13464325?hl=en)
- "Applications requesting access to restricted scopes must undergo an annual security assessment" (CASA, assurance levels AL1/AL2, revalidated yearly) — [Google Cloud: Security Assessment](https://support.google.com/cloud/answer/13465431?hl=en). Third-party estimates of cost vary from "a few hundred to a few thousand dollars per year" up to "$15,000 to $75,000" — [Deepstrike](https://deepstrike.io/blog/google-casa-security-assessment-2025); [Nango](https://nango.dev/docs/api-integrations/google-shared/google-security-review) (secondary, conflicting)
- Exemptions: verification is not needed "If the app is for your personal use (fewer than 100 users)", or in development/testing mode (100-user cap), or for internal Workspace apps — [Google Cloud: When verification is not needed](https://support.google.com/cloud/answer/13464323?hl=en)

**MCP OAuth client obligations (Boop connects to remote MCP servers)**
- MCP clients "MUST only allow `http://` and `https://` schemes for authorization URLs" and "MUST reject `javascript:`, `data:`, `file:`…". They "MUST NOT use shell commands" to open URLs. They "SHOULD require HTTPS for all OAuth-related URLs", "SHOULD block requests to private and reserved IP address ranges" during OAuth metadata discovery (SSRF), and should validate redirect hops. Mix-up attacks are mitigated by validating `iss`, and "PKCE alone does not prevent this attack". Clients should start with minimal scopes and step up incrementally — [MCP Security Best Practices (draft spec)](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- Token passthrough is "explicitly forbidden": MCP servers "MUST NOT accept any tokens that were not explicitly issued for the MCP server" — [same](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)

**Prompt-injection and agent hardening expectations**
- Willison's "lethal trifecta" (16 June 2025) is "Access to your private data", "Exposure to untrusted content", and "The ability to externally communicate". "The only way to stay safe there is to avoid that lethal trifecta combination entirely." A 95% detection rate is a failing grade, and MCP "encourages users to mix and match tools from different sources" — [Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- OWASP Top 10 for Agentic Applications 2026 (released 9 Dec 2025): ASI01 Agent Goal Hijack (instructions hidden in documents, emails or web pages) and ASI02 Tool Misuse. Recommended mitigations are least-agency tool scoping, parameter validation, and treating runtime-retrieved content as untrusted — [AIGL summary](https://www.aigl.blog/owasp-top-10-for-agentic-applications-2026/); [HUMAN Security](https://www.humansecurity.com/learn/blog/owasp-top-10-agentic-applications/) (secondary summaries of the OWASP document)

**OpenClaw (formerly Clawdbot/Moltbot) security incidents, 2026**
- **CVE-2026-25253** (CVSS 8.8): the Control UI "trusts gatewayUrl from the query string without validation and auto-connects on load, sending the stored gateway token". The result is one-click token theft leading to RCE, exploitable even on loopback-only instances because the victim's browser makes the connection. Fixed in 2026.1.29 (30 Jan 2026); GHSA-g8p2-7wf7-98mq — [The Hacker News](https://thehackernews.com/2026/02/openclaw-bug-enables-one-click-remote.html); [OSV](https://osv.dev/vulnerability/CVE-2026-25253); [GitLab advisory](https://advisories.gitlab.com/npm/clawdbot/CVE-2026-25253/)
- **ClawHub malicious skills ("ClawHavoc")**: Koi Security found 341 malicious skills out of 2,857, of which 335 came from one campaign delivering the AMOS infostealer. Later counts reached 824+ (Bitdefender, about 20% of the registry). Snyk found 283 skills (7.1%) leaking credentials in plaintext. OpenClaw responded with VirusTotal scanning of published skills — [Termdock](https://www.termdock.com/en/blog/clawhub-malicious-skills-incident); [Conscia](https://conscia.com/blog/the-openclaw-security-crisis/); [Particula](https://particula.tech/blog/openclaw-security-crisis-malicious-ai-agents) (secondary; figures vary by source)
- Exposed instances: estimates range from over 40,000 to about 135,000 internet-exposed gateways with unsafe defaults — [DigitalOcean](https://www.digitalocean.com/resources/articles/openclaw-security-challenges); [BetterClaw](https://www.betterclaw.io/blog/openclaw-security-2026) (secondary, inconsistent)
- OpenClaw's current SECURITY.md defines a trust model: "local-first agent infrastructure for trusted operators; it is not designed as a shared multi-tenant boundary". "Prompt injection without a policy, auth, approval, sandbox, or tool-boundary bypass" and "a malicious plugin after a trusted operator installs or enables it" are usually not vulnerabilities. Reports go through private GitHub Security Advisories or security@openclaw.ai, and maintainers may delete public disclosures. "We receive a high volume of AI-generated scanner findings", so reports need a PoC and demonstrated boundary crossing. There is no paid bug bounty — [OpenClaw SECURITY.md](https://raw.githubusercontent.com/openclaw/openclaw/main/SECURITY.md)

**Disclosure tooling and supply chain**
- GitHub private vulnerability reporting: researchers get a "Report a vulnerability" button on the repo's Advisories page. Maintainers can customise the form and require a CWE; it is enabled per repo under Advanced Security settings — [GitHub Docs](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/configuring-private-vulnerability-reporting-for-a-repository)
- Gradle dependency verification: `gradle/verification-metadata.xml` with SHA-256/512 checksums and PGP-trusted keys, bootstrapped via `./gradlew --write-verification-metadata sha256,pgp` and then reviewed. It "guards against compromised dependencies, not vulnerable ones"; strict mode is the default — [Gradle docs](https://docs.gradle.org/current/userguide/dependency_verification.html)
- GitHub artifact attestations sign build provenance with short-lived Sigstore certificates, are verifiable via `gh attestation verify`, and are free only for public repos. `actions/attest-build-provenance` v4 wraps `actions/attest`. GitHub positions this as a route to SLSA Build L3 — [GitHub Docs](https://docs.github.com/actions/security-guides/using-artifact-attestations-to-establish-provenance-for-builds); [GitHub blog](https://github.blog/enterprise-software/devsecops/enhance-build-security-and-reach-slsa-level-3-with-github-artifact-attestations/). Android projects (a Syncthing-Android fork) use this for APKs — [Syncthing forum](https://forum.syncthing.net/t/how-to-verify-researchxxl-syncthing-android-attestation/26072)
- OpenSSF Scorecard checks include Branch-Protection, Pinned-Dependencies, Signed-Releases and Token-Permissions (read-only GITHUB_TOKEN), each scored 0–10 and weighted by risk — [Microsoft NuGet blog](https://devblogs.microsoft.com/nuget/openssf-scorecard-for-net-nuget/)
- F-Droid/IzzyOnDroid reproducible builds let the developer keep their own signing key end-to-end (see section 2) — [F-Droid RB](https://f-droid.org/docs/Reproducible_Builds/)

### Inferences
- **Secrets policy for Boop:** commit nothing that is a real secret. That covers API keys, OAuth *client secrets* (Android clients have none), signing keystores, and Composio/backend tokens. OAuth *client IDs* and redirect URIs may live in source per flavour, as Thunderbird does, with a README note telling forks to register their own and change `applicationId` and redirect scheme. Add gitleaks or GitHub secret scanning with push protection in CI.
- **Gmail MCP:** for the open-source/FOSS build, ship *no* Google client ID. Instead offer a "Use your own Google Cloud OAuth client" setup, which qualifies as personal use (<100 users, no verification). Only the official Play build should carry a verified client. Budget for annual CASA if you request `gmail.readonly`/`modify`, or narrow to sensitive (non-restricted) scopes such as `gmail.send` where possible.
- **BYOK storage:** keep user API keys and OAuth refresh tokens encrypted with Tink AEAD backed by Android Keystore. Exclude them from Auto Backup (`dataExtractionRules`), never log them, and send them only to the provider host they belong to (pin per-provider base URLs; warn on custom base URLs).
- **Agent safety baseline (state it in SECURITY.md/THREAT_MODEL.md):**
  - Treat notifications, emails, web pages (jsoup), MCP tool results and screen text as untrusted data, never as instructions.
  - Require explicit human confirmation for side-effecting tools: UPI payment intents, Kite orders, food orders, sending email, launching intents. Show the exact parameters.
  - Per-tool allowlists and scopes. Never let one session combine private data (notifications/Gmail), untrusted content, and an outbound channel without a confirmation step.
  - Sandbox JavaScript in `androidx.javascriptengine` with no network/bridge by default.
  - Validate MCP OAuth URLs per the MCP spec MUSTs, and block private-IP SSRF in discovery.
  - Do not build a public "skills marketplace" without signing, review and scanning; that was ClawHub's failure mode.
- **SECURITY.md content:** supported versions; a private channel (GitHub PVR plus an email); expected response times; a trust model saying what counts as a vuln, for example "prompt injection that bypasses a confirmation gate = vuln; injection that only changes text = not"; and a rule against public PoCs before a fix. OpenClaw's file is a good template, especially its line about AI-generated scanner spam.
- **Supply-chain baseline:** Renovate or Dependabot for Gradle and Actions; Gradle dependency verification; Actions pinned by SHA with read-only token permissions; Scorecard Action; reproducible release builds from a clean tag on a pinned JDK and build-tools 34 apksigner; attestations on GitHub Release APKs; Play App Signing for Play with a separate upload key, and the upstream release key kept offline or in an HSM/Actions environment secret for GitHub/IzzyOnDroid/F-Droid-RB.

## 4. Trademarks and naming ("Boop", "Vanaras"), trademark policy for forks

### Takeaway
"Boop" is crowded. A US application for BOOP covering downloadable mobile schedule/routine software exists (Limejar Limited, filed 30 June 2020). A 2014 "Boop" messaging app existed. "Betty Boop" is an actively licensed character brand with its own app. "Vanaras" showed no conflicting app in a web search, but I did no registry search. Open-source licences grant copyright permissions, not trademark rights. Projects that want to stop confusing forks use a separate trademark policy, which can require renaming. Open WebUI instead wrote a branding clause into the licence, which made it non-OSI.

### Cited Findings
- Limejar Limited holds a **BOOP** US trademark application (Serial No. 90029294, filed 2020-06-30) for downloadable mobile software for schedule and routine management — [Justia Trademarks: Limejar Limited](https://trademarks.justia.com/owners/limejar-limited-4443016)
- A "Boop" messaging app (animated self-destructing messages, iOS and Android) launched in 2014 — [TechCrunch, 10 Nov 2014](https://techcrunch.com/2014/11/10/boop-messaging)
- A Betty Boop app exists under the character's licensing programme — [License Global](https://www.licenseglobal.com/character/betty-boop-app-hits-market)
- Boop, LLC holds marks (for example BESTIE) for pet-services scheduling apps — [Justia: Boop, LLC](https://trademarks.justia.com/owners/boop-llc-6013608)
- A web search for "Vanara" Android AI assistants found no app by that name; near-names include Ara (GPL-3.0 assistant on the F-Droid RFP tracker), Kiara, AvvA and Vani — [F-Droid RFP #1181](https://gitlab.com/fdroid/rfp/issues/1181); [Dealroom: Vani](https://app.dealroom.co/companies/vani)
- NLnet's NGI0 guidance (German-law framing): all open-source licences permit forking under copyright, while trademarks are a separate regime — [NLnet: Forking and Trademarks](https://NLnet.nl/NGI0/bestpractices/Forking_and_Trademarks.pdf)
- Examples of policy approaches: some project trademark policies require forks to rename but say they target only impersonators; others (a registered EU mark) bar forks from using the name as the dominant part of their own name — [Mushi Mushi TRADEMARK.md](https://raw.githubusercontent.com/kensaurus/mushi-mushi/HEAD/TRADEMARK.md); [Stagewise trademark policy](https://stagewise.io/trademark-policy)
- Open WebUI's licence clause bans removing "Open WebUI" branding above 50 users and requires public forks to disclose they are unofficial. The project acknowledges this makes it non-OSI — [Open WebUI licence docs](https://docs.openwebui.com/license/)
- Thunderbird requires forks to use their own OAuth clients and a different `redirectUri`. This is a technical identity separation that complements trademark rules — [Thunderbird README](https://raw.githubusercontent.com/thunderbird/thunderbird-android/main/README.md)

### Inferences
- Before launch, run proper searches: the USPTO (Class 9 software, Class 42 SaaS), the Indian TM Registry (Class 9/42), EUIPO, and the Play Store/F-Droid for "Boop". The Limejar Class 9 "mobile software" filing could cause a likelihood-of-confusion problem for an assistant app. A more distinctive compound name, such as "Boop Assistant", may still conflict. "Vanaras" looks less crowded in app stores, but it is a mythological term (descriptiveness and ownership need checking).
- Publish a short TRADEMARKS.md, kept separate from the Apache-2.0 LICENSE (Apache-2.0 §6 already withholds trademark rights). Allow nominative use ("based on Boop"). Require renamed forks with a different `applicationId`, icon and OAuth clients. Reserve the name and icon for official builds. Consider registering the mark in India first.

- No USPTO, Indian TM Registry or EUIPO search was performed; the status of the Limejar application (registered, abandoned, live) is unknown.
- No search of the Play Store for current "Boop" app listings.
- No legal source on Indian trademark practice for open-source names.

## 5. Contribution model and sustainability: DCO vs CLA, governance, CoC, templates, growth and funding, pitfalls

### Takeaway
A DCO (sign-off per commit) is the low-friction default. Home Assistant uses DCO-style text even though the file is named "CLA.md". A real CLA (Signal, Open WebUI) is what made later relicensing possible, so contributors increasingly read CLAs as rug-pull insurance for the owner (Open WebUI 2025, Redis 2024, HashiCorp 2023). Successful assistant projects grew with a strong plugin boundary and strict PR rules (OpenClaw), and funded themselves via a foundation plus commercial partner (Home Assistant/Nabu Casa; OpenClaw Foundation sponsored by OpenAI, NVIDIA, Microsoft and Tencent) or an enterprise licence (Open WebUI). Maintainer burnout is the default outcome: about 60% of maintainers are unpaid and about 60% have quit or considered quitting.

### Cited Findings

**DCO vs CLA**
- CERN OSPO recommends DCO for its projects. It notes a CLA "can include copyright transfer, which generally eases the life of project managers (eg in case of re-licensing)", and that the DCO/CLA choice affects any later relicensing — [CERN OSPO](https://ospo.docs.cern.ch/recommendations/CLAs-and-DCOs)
- In Django's CLA-vs-DCO discussion, moving to a DCO would mean losing the ability to relicense Django in future. A DCO sign-off is needed on every commit — [Django forum](https://forum.djangoproject.com/t/cla-vs-dco-for-django-contributors/42399); also [opensource.com: CLA vs DCO](https://opensource.com/article/18/3/cla-vs-dco-whats-difference); [FINOS OSR](https://osr.finos.org/docs/bok/Artifacts/CLAs-And-DCOs)
- Home Assistant's `CLA.md` is DCO-style certification text: "By making a contribution to this project, I certify that: (a) The contribution was created in whole or in part by me and I have the right to submit it under the Apache 2.0 license…" — [home-assistant/core CLA.md](https://raw.githubusercontent.com/home-assistant/core/dev/CLA.md). The HA Android app has the same file — [home-assistant/android CLA.md](https://raw.githubusercontent.com/home-assistant/android/main/CLA.md)
- Signal requires signing its CLA before a PR can be merged, and its issue tracker is "for bugs, not feature requests" (features go to the community forum) — [Signal-Android CONTRIBUTING](https://raw.githubusercontent.com/signalapp/Signal-Android/main/CONTRIBUTING.md)
- Open WebUI: "By contributing to this project, you agree to the project's Contributor License Agreement". This came alongside the v0.6.6 licence change, and earlier contributions stay BSD-3 — [LICENSE](https://raw.githubusercontent.com/open-webui/open-webui/main/LICENSE); [licence docs](https://docs.openwebui.com/license/)

**Licence rug-pulls and lessons**
- Redis moved from BSD-3 to RSALv2/SSPLv1 in 2024 (v7.4). AWS and Google backed the Valkey fork under the Linux Foundation. On 1 May 2025 Redis added AGPLv3, and the CEO admitted the change "hurt developer relations" — [The Register](https://www.theregister.com/2025/05/01/redis_returns_to_open_source/); [Phoronix](https://www.phoronix.com/news/Redis-8.0-Goes-AGPLv3)
- HashiCorp moved Terraform and Vault from MPL-2.0 to BSL 1.1 in 2023, which led to the OpenTofu and OpenBao forks under the Linux Foundation. It has not been reversed — [WZ-IT licence change chronicle](https://wz-it.com/en/blog/open-source-licence-change-chronicle/)
- The Jan AGPL→Apache change drew contributor-consent questions that I found unanswered — [r/LocalLLaMA (redlib mirror)](https://redlib.ssps.io/r/LocalLLaMA/comments/1ksjkhb/jan_is_now_apache_20)

**Governance and contributor management at scale (OpenClaw)**
- Rules: bugs and small fixes go straight to PR. "New features / architecture → Start a GitHub Issue… Most features are not accepted and should be third party plugins instead using our plugin SDK". Refactor-only and test/CI-only PRs are not accepted. Routing uses issue forms and CODEOWNERS ("Do not guess who to tag"). "For agent-authored or otherwise non-trivial work, create or reuse the issue first". There is a hard cap of **20 open PRs per author**, with auto-close — [OpenClaw CONTRIBUTING.md](https://raw.githubusercontent.com/openclaw/openclaw/main/CONTRIBUTING.md)
- Governance: the OpenClaw Foundation is described as a US 501(c)(3), chaired by Dave Morin, with sponsors including OpenAI, NVIDIA, Microsoft and Tencent. Founder Peter Steinberger (hired by OpenAI in February 2026) "continues to make the decisions, especially the technical ones" — [The New Stack](https://thenewstack.io/openclaw-foundation-nonprofit-status/); [Trending Topics](https://www.trendingtopics.eu/opwnclaw-foundation-launches-with-openai-nvidia-microsoft-and-tencent-as-sponsors/); [Verdent guide](https://www.verdent.ai/guides/openclaw/founder). Security work is shared with engineers from NVIDIA and Tencent — [SECURITY.md](https://raw.githubusercontent.com/openclaw/openclaw/main/SECURITY.md)

**Funding models**
- Home Assistant: the Open Home Foundation (a nonprofit, announced April 2024) owns Home Assistant, ESPHome and 240+ projects. Nabu Casa (for-profit) runs Home Assistant Cloud and sells hardware as a commercial partner, paying a partner fee and contributing most hardware profits. Cloud subscriptions "help fund Nabu Casa's partner fee and pay the salaries" of foundation staff. The stated aim is a bulwark against "the risk of buyout, and open-source projects becoming abandonware" — [Announcing the Open Home Foundation](https://www.openhomefoundation.org/blog/announcing-the-open-home-foundation/); [OHF organisation](https://openhomefoundation.org/organization); [CNX Software](https://www.cnx-software.com/2024/04/23/open-home-foundation-manage-home-assistant-esphome-zigpy-over-240-open-source-smart-home-projects/). Home Assistant reported "2 million homes" in April 2025 — [State of the Open Home 2025](https://home-assistant.io/blog/2025/04/16/state-of-the-open-home-recap/). Apollo Automation became a second commercial partner at the end of 2025 — [Apollo Automation](https://apolloautomation.com/blogs/news/who-owns-home-assistant-the-open-home-foundation-nabu-casa-and-apollo-automation-explained)
- Open WebUI: an enterprise licence is one of the exceptions to its branding clause, an open-core-ish monetisation path — [Open WebUI licence docs](https://docs.openwebui.com/license/)
- OpenClaw: corporate sponsorship of a foundation (see above).

**Burnout**
- Tidelift's 2024 maintainer report: 60% of maintainers are unpaid; 60% have quit or considered quitting; maintainers spend about 3× more time on security than three years earlier. About 400 respondents — [The Register, 18 Sep 2024](https://www.theregister.com/2024/09/18/open_source_maintainers_underpaid/); [TFiR](https://tfir.io/tidelift-study-reveals-that-60-of-maintainers-still-dont-get-paid-for-their-work/)
- OpenClaw explicitly reports a "high volume of AI-generated scanner findings" in security reports, a new maintainer-load vector — [SECURITY.md](https://raw.githubusercontent.com/openclaw/openclaw/main/SECURITY.md)

### Inferences
- **For Boop:** use a DCO (the GitHub DCO app or a probot check) plus an Apache-2.0 inbound=outbound policy, and say publicly that you will not use a CLA. This is a credible "no rug-pull" signal, at the cost of not being able to relicense later. If a future hosted/enterprise offering is likely, decide *now*. A CLA added later (as Open WebUI did) is what users read as a rug-pull.
- **Governance:** start as a BDFL with a written GOVERNANCE.md covering decision rights, how maintainers are added, and succession. Revisit a fiscal host (Open Collective / a Linux Foundation-style umbrella) once there are more than 3 regular maintainers or corporate sponsors. A foundation is a later step and is what the high-profile projects did.
- **Contribution hygiene modelled on OpenClaw and Signal:**
  - Issue-first for features.
  - A plugin/MCP boundary so "integrations" (Swiggy, Zomato, Kite, Composio) live as optional modules or remote MCP configs rather than core PRs.
  - YAML issue forms (bug, feature, integration request, security redirect).
  - A PR template with "AI-assisted?" disclosure and test evidence.
  - A per-author open-PR cap.
  - `good first issue` / `help wanted` labels, a public ROADMAP.md (or GitHub Project), and CODE_OF_CONDUCT.md (Contributor Covenant).
- **Sustainability options ranked for a solo or small-team Android app:**
  1. GitHub Sponsors / Open Collective / Liberapay (F-Droid lets you list verified donation links).
  2. A paid Play build: same source, convenience and auto-updates; legal under Apache-2.0.
  3. An optional hosted relay or "Boop Cloud" for push, sync or managed MCP OAuth, à la Nabu Casa; keep it optional to avoid NonFreeNet/TetheredNet.
  4. Grants: NLnet/NGI Zero (EU) for privacy-preserving on-device AI, FOSS United in India.
  Avoid open-core features that make the FOSS flavour crippled.

- Did not fetch the Tidelift primary PDF; figures come from press coverage.
- Did not verify whether Leon or Jan use a DCO or CLA. Did not check NewPipe's CONTRIBUTING for CLA/DCO (the file exists).
- No data on contributor-growth tactics, such as how fast first-time contributors convert, for AI-assistant projects specifically.

## 6. Privacy and regulatory obligations (India, EU) when open-sourcing and distributing the app

### Takeaway
Open-sourcing does not remove privacy duties for whoever *distributes* builds. On Play, a privacy policy and a Data safety form are mandatory for every app. Data sent off-device to LLM/MCP providers must be declared, and SDK collection (ML Kit sends usage metrics to Google) is the developer's responsibility to disclose. Play clarified in July 2026 that user-data rules cover third-party AI integrations. In India, the DPDP Rules 2025 were notified 14 Nov 2025 and phase in: consent managers around Nov 2026, core notice/consent/breach/rights duties from 13 May 2027. In the EU, the AI Act Art. 50 chatbot-disclosure duty applies from 2 Aug 2026 (not delayed by the Digital Omnibus). CRA vulnerability reporting for manufacturers started 11 Sep 2026; non-commercial open source is largely out of scope, and lighter "steward" duties apply to organisations backing OSS used commercially.

### Cited Findings
- **Play Data safety:** "All developers that have an app published on Google Play must complete the Data safety form", "Even developers with apps that do not collect any user data". A privacy policy is required. Data "only processed locally on the user's device… does not need to be disclosed". Off-device ephemeral processing must be included in the form but is not shown on the listing. "You must reflect data collection or sharing carried out by such third-party code [SDKs]". User-initiated transfers and service providers acting on the developer's behalf may be exempt from "sharing" — [Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en)
- **ML Kit:** input data is processed on-device, but ML Kit contacts Google servers for model updates and sends "performance and usage metrics". "You are responsible for informing users of your app about Google's processing of ML Kit metrics data" — [ML Kit Terms](https://developers.google.com/ml-kit/terms)
- **Play, July 2026:** User Data policy requirements "also apply to third-party AI integrations"; developers remain responsible for limited use, disclosure and consent. New Data safety guidance covers precise and approximate location — [Play announcement 15 July 2026](https://support.google.com/googleplay/android-developer/answer/17134731?hl=en-GB)
- **Accessibility disclosures** cannot be only in the privacy policy or ToS and cannot be bundled with other disclosures — [Play Accessibility policy](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)

### Inferences
- **Privacy policy for Boop must be explicit about:**
  - BYOK flows: prompts, notification text, screen text and email content are sent directly from the device to the provider the user chose (Anthropic, OpenAI, Google, OpenRouter) under that provider's terms. Boop operates no server, if true.
  - MCP providers (Swiggy, Zomato, Zerodha, Composio, Google).
  - Gemini Live audio streaming.
  - ML Kit metrics.
  - Notification and accessibility data handling.
  - Retention: local only, encrypted with Tink.
  - Children: not for under-18s, which matters under DPDP's verifiable parental consent rules.
  - A grievance contact. DPDP requires a contact for data principals; for an Indian developer, name one.
- **Data safety:** declare messages, emails, app activity, audio, financial info (if Kite/UPI data leaves the device to MCP servers) and "other user-generated content". Mark them as shared with or collected by third-party AI services, and decide case by case whether the user-initiated exemption applies. Declare ML Kit's diagnostics.
- **Telemetry:** ship with **no analytics** in the FOSS flavour; the F-Droid "Tracking" anti-feature applies if reporting is on "by default". If crash reporting is needed in the Play flavour, make it opt-in (consent before collection), which is also the safer reading under GDPR/ePrivacy and DPDP consent rules. Prefer self-hostable tools (ACRA to your own endpoint) over Firebase Crashlytics.
- **AI Act Art. 50:** show "You're talking to an AI" in the first-run UI and voice mode. Label AI-generated outputs where they could be mistaken for human-authored (for example, emails Boop drafts and sends).
- **CRA:** an individual developer publishing a free, non-monetised app is likely outside "commercial activity". A paid Play build, a hosted service or a company backing the project could make Boop a "product placed on the market" (manufacturer duties, including 24h/72h reporting) or make the backing entity a steward. Keep the SECURITY.md/incident process anyway; it is required for stewards and is cheap.

# Memory write and maintenance for LLM personal assistants: extraction, dedupe, update, conflicts, time, tidy-up, forgetting (judged for a ~2B on-device assistant)

Scope note: this file covers how memories are WRITTEN and KEPT CLEAN. Retrieval/ranking and training the model to read notes are covered elsewhere and appear here only where they affect writing. Dates are first-submission dates unless stated. "Phone-fit" judgements are in the Inferences subsections.

## Q1. How do MemGPT/Letta, Generative Agents, MemoryBank, Mem0, A-MEM, Zep/Graphiti, LangMem and similar systems extract, dedupe, update, invalidate and forget? Exact mechanisms and thresholds

### Takeaway
Almost every published system uses the same pattern: an LLM pulls candidate facts out of each new turn, then an embedding search finds roughly the 5 to 10 nearest existing memories, then a second LLM decision chooses add, merge, invalidate or skip. The numeric settings are small and copyable (recent-message window of 4 to 10, top-k of 5 to 10, cosine or Jaccard cut-offs of 0.6 to 0.9). The 2025-2026 trend is away from destructive UPDATE/DELETE and toward adding new facts and marking old ones invalid with timestamps (Zep/Graphiti from the start, Mem0 since April 2026). Forgetting is mostly done as down-ranking (recency decay) rather than deletion.

### Cited Findings

**Mem0 (paper Apr 2025; GPT-4o-mini as the memory LLM)**
- Extraction runs on each new message pair (m_{t-1}, m_t). The extractor also sees an asynchronously refreshed conversation summary S and the previous m messages, with m = 10. — [Mem0 paper, arXiv 2504.19413](https://arxiv.org/html/2504.19413)
- Update: for each candidate fact, the top s = 10 most similar memories are retrieved by embedding. The LLM then picks ADD / UPDATE / DELETE / NOOP through a function-calling "tool call", with no separate classifier. Appendix B: UPDATE replaces only when the new fact has more information; DELETE removes a contradicted memory. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Mem0g (graph variant): an LLM extracts entities and (source, relation, destination) triplets. Nodes are reused when embedding similarity exceeds a threshold t (the value is not given in the extracted text). An LLM "update resolver" marks conflicting relationships **invalid rather than deleting them**, "to enable temporal reasoning". — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Mem0's open-source extraction prompt has 7 categories to remember: preferences, personal details, plans/intentions, activity/service preferences, health/wellness, professional details, misc favourites. Its negative few-shots include `Hi.` → `{"facts": []}` and `There are branches in trees.` → `{"facts": []}`. The user-only variant says "GENERATE FACTS SOLELY BASED ON THE USER'S MESSAGES. DO NOT INCLUDE INFORMATION FROM ASSISTANT OR SYSTEM MESSAGES." Today's date is injected at runtime. — [mem0/configs/prompts.py](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py)
- Mem0's update prompt says "keep the fact which has the most information". It treats near-synonyms ("Likes cheese pizza" vs "Loves cheese pizza") as no change. On contradiction ("Dislikes cheese pizza") it DELETEs the old memory. It must reuse input IDs for UPDATE/DELETE and never invent IDs. — [mem0 prompts.py](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py)
- **Mem0 V3 (April 2026) dropped UPDATE/DELETE.** The new `ADDITIVE_EXTRACTION_PROMPT` says "Your sole operation is ADD". Existing memories are used "ONLY for deduplication and linking". A contradiction becomes a `linked_memory_ids` link, not a delete. The prompt says "When in doubt, extract… The deduplication system downstream will handle true duplicates." — [mem0 prompts.py](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py)
- Mem0's stated reason for the change: the two-pass reconcile step was slow, "overwrites could erase key information from the original fact, and deletes could remove details needed later". Now there is one LLM call per add(). Changed facts (e.g. a move from New York to San Francisco) are kept as two records with temporal context. — [Mem0 blog, "token-efficient memory algorithm", Apr 16 2026](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm); [Mem0 v2→v3 migration doc](https://docs.mem0.ai/migration/platform-v2-to-v3)
- The migration doc warns that memory counts will grow. For hard limits it suggests "the memory expiration feature or periodic cleanup". Its default search `threshold` moved to 0.1 from 0.3; this is a retrieval filter, not a dedupe threshold. The public docs do not describe the dedupe method. — [Mem0 migration doc](https://docs.mem0.ai/migration/platform-v2-to-v3)

**Zep / Graphiti (paper Jan 2025; gpt-4o-mini for graph building, BGE-m3 embeddings)**
- Three layers. (1) Raw "episodes" (messages) are kept as a non-lossy source. (2) An entity/fact graph is built from them. (3) Community summaries are found by label propagation. — [Zep paper, arXiv 2501.13956](https://arxiv.org/html/2501.13956)
- Entity extraction uses the current message plus the last n = 4 messages. The speaker is always an entity. A Reflexion-style self-check reduces hallucination. Entity resolution: names are embedded (1024-d) for cosine search, a full-text search runs in parallel, then an LLM prompt returns `is_duplicate` and the existing uuid plus a merged name/summary. Graph writes use fixed Cypher templates, not LLM-written queries, "to reduce hallucinations". — [Zep paper](https://arxiv.org/html/2501.13956)
- Fact (edge) dedupe searches only edges between the same entity pair. A fact-resolution prompt returns `is_duplicate`. — [Zep paper](https://arxiv.org/html/2501.13956)
- Bi-temporal edges: t_valid/t_invalid (when true in the world) and t'_created/t'_expired (when entered or retired in the system). When a new edge contradicts an overlapping old one, the old edge's t_invalid is set to the new edge's t_valid. Old edges are invalidated, not deleted. — [Zep paper](https://arxiv.org/html/2501.13956)
- Relative dates ("two weeks ago") are resolved against a reference timestamp to ISO 8601. Present-tense facts get valid_at = reference time. Dates are set only when they change the relationship itself; otherwise they are null. — [Zep paper](https://arxiv.org/html/2501.13956)
- Graphiti's current edge-resolution prompt rules: "NEVER mark facts as contradicted unless the new fact explicitly makes the old fact false"; "Only mark a fact as contradicted when the NEW FACT and the existing fact cannot both be true"; "A contradiction requires explicit evidence that the old fact stopped being true or was replaced"; "Do NOT infer contradiction from recency alone…"; "NEVER mark facts as duplicates if they have key differences, particularly around numeric values, dates, or key qualifiers." — [graphiti dedupe_edges.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/prompts/dedupe_edges.py)
- Graphiti has a **deterministic, no-LLM entity dedupe pass** that runs before the LLM. Names are normalised (lowercase, whitespace collapsed). An exact match with exactly one existing node resolves straight away. Fuzzy path: names shorter than 6 characters *and* under 2 tokens are skipped, and names must have Shannon character entropy ≥ 1.5. Matching uses 3-character shingles, MinHash with 32 permutations, LSH bands of 4, and resolution only when Jaccard ≥ 0.9. Anything ambiguous goes to the LLM. — [graphiti dedup_helpers.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/utils/maintenance/dedup_helpers.py)

**A-MEM (Feb 2025)**
- Each note stores: original content, timestamp, LLM-generated keywords (≥3), tags (≥3), a one-sentence context, an embedding (all-MiniLM-L6-v2) of all of these, and links. — [A-MEM, arXiv 2502.12110](https://arxiv.org/html/2502.12110)
- Link generation: cosine top-k (k = 10 by default; k = 10 in every category for Qwen2.5-1.5B and Llama3.2-1B; 40 to 50 for GPT-4o models), then the LLM decides which links to make. — [A-MEM](https://arxiv.org/html/2502.12110)
- "Memory evolution": for each neighbour, the LLM rewrites that neighbour's context and tags, and the new version **replaces** the old one. "Merge" and "prune" appear as prompt options but are never defined. The paper describes no deletion, dedupe or conflict handling. — [A-MEM](https://arxiv.org/html/2502.12110)
- Cost: about 1,200 tokens per memory operation; 5.4 s per operation with GPT-4o-mini and 1.1 s with local Llama 3.2 1B on a single GPU. — [A-MEM](https://arxiv.org/html/2502.12110)

**Generative Agents (Apr 2023)**
- Importance is scored 1 to 10 by the LLM when a memory is written. Examples: brushing teeth = mundane, breakup = poignant, "cleaning up the room" = 2, "asking your crush out on a date" = 8. — [Generative Agents, arXiv 2304.03442](https://ar5iv.labs.arxiv.org/html/2304.03442)
- Recency is an exponential decay of 0.995 per game-hour since last retrieval. Retrieval score = recency + importance + relevance, each min-max normalised, all weights 1. — [Generative Agents](https://ar5iv.labs.arxiv.org/html/2304.03442)
- Reflection (consolidation into higher-level insights) fires when the summed importance of recent events exceeds 150, "roughly two or three times a day". Steps: take the 100 most recent records → ask for 3 salient questions → retrieve for each → ask for 5 insights, each citing evidence records ("insight (because of 1, 5, 3)"). — [Generative Agents](https://ar5iv.labs.arxiv.org/html/2304.03442)
- Ablation (TrueSkill μ): full 29.89, no reflection 26.88, no reflection or planning 25.64, human crowdworker 22.95, no memory/planning/reflection 21.21. — [Generative Agents](https://ar5iv.labs.arxiv.org/html/2304.03442)

**MemoryBank (May 2023)**
- Forgetting uses the Ebbinghaus curve R = e^(−t/S). S starts at 1 when an item is first mentioned; each recall adds 1 to S and resets t to 0. The authors call it "an exploratory and highly simplified memory updating model". No deletion threshold is given. — [MemoryBank, arXiv 2305.10250](https://ar5iv.labs.arxiv.org/html/2305.10250)
- Builds daily event summaries → a global summary, and daily personality insights → a global user portrait. — [MemoryBank](https://ar5iv.labs.arxiv.org/html/2305.10250)
- With a 6.2B model (ChatGLM): English retrieval accuracy 0.809 but correctness 0.438. ChatGPT: 0.763 / 0.716. So small models retrieved fine but answered worse. — [MemoryBank](https://ar5iv.labs.arxiv.org/html/2305.10250)

**MemGPT / Letta (Oct 2023 → 2026)**
- The main context has read-only system instructions, a fixed-size read/write "working context" (core memory) editable only via function calls, and a FIFO message queue. At a warning point (e.g. 70% of context) the system tells the LLM to save important content. At flush (e.g. 100%) it evicts about 50% of messages into a recursive summary; evicted messages stay searchable in recall storage. The LLM itself decides what to write ("entirely self-directed"). — [MemGPT, arXiv 2310.08560](https://ar5iv.labs.arxiv.org/html/2310.08560)
- MemGPT with GPT-3.5 degraded significantly "due to limited function-calling ability". — [MemGPT](https://ar5iv.labs.arxiv.org/html/2310.08560)
- Letta's current background consolidation ("dreaming" / sleep-time): background subagents "review recent conversations, consolidate useful lessons, and update memory". It runs "after a set number of completed agent steps or when the context window is compacted". An optional "Agent reviews before applying" pass revises proposed updates in a second background conversation. — [Letta sleep-time/dreaming docs](https://docs.letta.com/guides/agents/architectures/sleeptime)

**LangMem (LangChain, 2025)**
- Two modes: hot path (the agent writes while chatting; adds latency) and background ("subconscious") formation after a conversation or after inactivity. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- "Profiles" are one document holding current state that is updated in place. "Collections" are separate records that can be inserted. The guide notes over-extraction lowers precision and under-extraction lowers recall. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- `create_memory_manager` defaults: `enable_inserts=True, enable_updates=True, enable_deletes=False`; the store manager uses `query_limit=5`. `ReflectionExecutor.submit(..., after_seconds=…)` delays background work to "debounce and deduplicate reflection work". (The docstring says deletes default to True, contradicting the signature.) — [LangMem API reference](https://langchain-ai.github.io/langmem/reference/memory/)

**MemoryOS (Jun 2025): deterministic promotion and eviction**
- Short-term memory is a 7-page queue, FIFO into mid-term. A page joins a topic segment when its match score > θ = 0.6. Max segment length 200; when exceeded, the lowest-heat segment is evicted. — [MemoryOS, arXiv 2506.06326](https://arxiv.org/html/2506.06326)
- Heat = N_visit + L_interaction + exp(−Δt/μ), all weights 1, μ = 1e7 seconds. Segments with heat > τ = 5 are promoted to long-term persona memory, and L_interaction then resets. The user knowledge base and agent traits are each 100-entry FIFO queues. — [MemoryOS](https://arxiv.org/html/2506.06326)

**Mem0 Memory Decay (vendor blog, May 2026)**
- A per-project toggle that rescales search scores by last retrieval time: up to 1.5× for recently used memories, floor 0.3× for idle ones. It is "a soft re-rank, not a filter", so nothing is deleted. `delete(delete_linked=True)` removes a fact and the chain it superseded. Details come from vendor material via search snippets. — [Mem0 blog: introducing memory decay](https://mem0.ai/blog/introducing-memory-decay-in-mem0)

### Inferences
- **Copyable thresholds and settings for Maya, ranked by phone-fit:**
  1. No model needed: Graphiti-style exact-normalised match, then MinHash/Jaccard ≥ 0.9 near-duplicate check, with an entropy/length gate.
  2. EmbeddingGemma only: cosine top-5 to top-10 candidates per new fact (Mem0 s = 10; LangMem query_limit = 5), plus a cosine "same fact" cut-off. nanoMuse's 0.8 is in the same range as MemoryOS's θ = 0.6 topic-join. Neither paper's threshold was tuned for EmbeddingGemma, so Maya must calibrate its own on labelled pairs.
  3. Needs an LLM decision: duplicate/contradict judgements, importance scores, reflection.
- The Mem0 2026 reversal is strong evidence. The best-known vendor of LLM-driven UPDATE/DELETE found that destructive reconcile lost information and moved to add-only + link + time-aware retrieval. For a 2B model, whose UPDATE/DELETE judgement is weaker than GPT-4o-mini's, the case against letting the model delete or overwrite is even stronger.
- Generative-Agents reflection (100 records → 3 questions → 5 insights with citations) and A-MEM evolution (rewriting neighbours) are multi-step reasoning jobs. On a 2B 4-bit model they are likely to multiply junk. A-MEM's evolution also overwrites neighbours without history. Treat both as cloud-model or "never" techniques for Maya, or limit them to read-only suggestions.
- Down-ranking (Generative Agents recency 0.995/h, Mem0 0.3× floor, MemoryBank strength) is safe on a phone: it is arithmetic over timestamps and recall counts, with no model and no deletion.

### Gaps
- Mem0's V3 dedupe method (hash? cosine threshold?) is not documented in the pages fetched.
- The Mem0g node-merge threshold t value was not in the extracted paper text.
- The Letta docs fetched did not list the memory-edit tool names (memory_rethink, memory_replace, etc.) or block character limits; I did not verify them.
- I did not find the Generative Agents importance-score distribution or how often 1-10 scores were wrong.

## Q2. What do papers report about extraction quality and noise (false facts, hypotheticals, jokes, questions taken as facts), how is it filtered, and what are the numbers for small models?

### Takeaway
Independent measurements show that production extractors miss most facts and that what they store is often wrong. The worst documented case is a 2B Gemma model doing Mem0 extraction, which produced a store that was 97.8% junk, and a single hallucination multiplied 808 times through a recall → re-extract feedback loop. The filters that work are mostly outside the extracting model: user-only input, negative few-shots, an entailment check against the source utterance, never re-extracting from recalled memories, and a quality gate before storage.

### Cited Findings
- **Mem0 issue #4573 (Mar 27 2026), "What we found after auditing 10,134 mem0 entries: 97.8% were junk".** Covers one agent and one human over 32 days. **Extraction ran on gemma2:2b (local, Ollama) for the first 20 days**, then Claude Sonnet 4.6. Only 38 entries were "clean enough to keep as-is". — [mem0 issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- Junk breakdown in that audit: system-prompt/boot-file restating 3,200 (52.7%); heartbeat/cron noise 700 (11.5%); architecture dumps 500 (8.2%); transient task state 450 (7.4%); **hallucinated user profiles 315 (5.2%)**; identity confusion 200 (3.3%); security/privacy leaks 130 (2.1%); wrong locations 60 (1.0%); fabricated lifestyle 50 (0.8%). Duplicates were handled separately: 2,468 removed by hash/sweeps, then 1,572 by cosine dedupe, out of 2,943 flagged near-duplicates ("37.6% of what remained"). — [mem0 issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- **Feedback loop:** 808 entries said "User prefers Vim" (191 exact copies). The 2B model hallucinated it once; it was stored, recalled into context, and re-extracted in later sessions. "The model caused the initial hallucination, but the pipeline caused it to multiply." Proposed fixes, in order of impact: (1) mark recalled memories so extraction skips them; (2) a quality gate between extraction and storage; (3) negative few-shot examples; (4) a REJECT action in the update prompt; (5) identity-aware extraction. — [mem0 issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- After four config changes the reporter's 48-hour sample was still 34/73 = 46.6% junk. The issue was closed in June 2026, citing the add-only algorithm (Apr 2026), Memory Decay (May 2026) and Temporal Reasoning (Jun 2026). The maintainer's closing note says "extraction-prompt permissiveness, feedback loops, and identity-aware extraction remain ongoing areas of improvement". — [mem0 issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- A secondhand summary (Jamgate README, via search) says a frontier-model-extracted batch in the same audit was still 89.6% junk. I could not verify this in the issue text I fetched. — [search result summary of Jamgate README](https://socket.dev/npm/package/jamgate/diff/0.11.2)
- **HaluMem (Nov 2025)** is an operation-level benchmark: 14,948 gold memory points and 3,467 QA in the Medium set (~160k tokens per user). On Medium, Mem0 has memory recall 42.91%, target precision 86.26%, accuracy 60.86% and false-memory resistance 56.80%. Memobase: recall 14.55%. MemOS: recall 74.07% but FMR 44.94%. "Apart from MemOS, every system has recall below 60%… every system's memory accuracy is below 62%." — [HaluMem, arXiv 2511.03506](https://arxiv.org/html/2511.03506)
- HaluMem updates: update hallucination is < 2% for every system, but **omission is above 50% for most** (Mem0 74.02% omitted on Medium, 98.51% on the 1M-token Long set). The authors attribute omission mainly to weak extraction coverage. QA accuracy tracks extraction quality; every system is < 70%. The authors argue hallucinations "are generated and accumulated during extraction and updating, then propagate to QA". — [HaluMem](https://arxiv.org/html/2511.03506)
- **LongMemEval (Oct 2024):** Coze "often failed to record indirectly provided user information". ChatGPT "tended to overwrite crucial information as the chat continues". On a 97-question subset with GPT-4o: offline reading 0.9184, ChatGPT memory 0.5773, Coze 0.3299. — [LongMemEval, arXiv 2410.10813](https://arxiv.org/html/2410.10813)
- LongMemEval used Llama 3.1 8B Instruct to extract facts, keyphrases and timestamped events at indexing. For time-range extraction from queries, only GPT-4o helped; Llama 3.1 8B "often hallucinat[es] or miss[es] temporal cues". — [LongMemEval](https://arxiv.org/html/2410.10813)
- **Persona-NLI (Jan 2024):** a BART-Large persona-triple extractor trained without negative examples "always extracted [a relation], regardless of the input". Filtering with a fine-tuned nli-deberta-v3-base entailment classifier removed about 90% of extractions (41,709 → 4,030). Human acceptance rose only slightly with greedy decoding (0.64 → 0.68) and fell with beam search (0.63 → 0.52). The classifier's own held-out precision was 0.94. — [Using NLI to Improve Persona Extraction, arXiv 2401.06742](https://arxiv.org/html/2401.06742v1)
- Mem0's extraction prompt fights noise with negative few-shots (greetings and general-knowledge statements → empty list) and by restricting the source to user messages. — [mem0 prompts.py](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py)
- Mem0 V3 went the other way on permissiveness: "When in doubt, extract", relying on downstream dedupe. It now stores agent-generated facts "with the same weight as user-stated facts". — [mem0 prompts.py](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py); [Mem0 blog](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)
- Zep adds a Reflexion-style self-check after entity extraction to reduce hallucinated entities, and uses fixed Cypher templates rather than LLM-generated writes. — [Zep paper](https://arxiv.org/html/2501.13956)
- Generative Agents saw memory "embellishment": agents added details never discussed, and one conflated a character with the 18th-century economist Adam Smith. 1.3% (6/453) of answers about knowing other agents were hallucinated. — [Generative Agents](https://ar5iv.labs.arxiv.org/html/2304.03442)
- **Small-model memory managers:** in Memory-R1 (Aug 2025; ACL 2026) the full pipeline with untrained Qwen-2.5-3B scores LoCoMo F1 24.18 / J 41.24. With RL training of the memory manager and answer agent on **only 152 QA pairs** it reaches 38.42 / 54.40 (PPO) and 40.45 / 57.92 (GRPO). With LLaMA-3.1-8B: Mem0 J 45.68, A-Mem 44.76, Zep 42.80, Memory-R1-GRPO 62.74. — [Memory-R1, arXiv 2508.19828](https://arxiv.org/html/2508.19828v4)
- A-MEM ran its whole note/link/evolve pipeline with Qwen2.5-1.5B/3B and Llama3.2-1B/3B and beat the baselines on every LoCoMo category, but absolute F1 stayed low (e.g. Llama3.2-1B single-hop 28.51, multi-hop 19.06; Qwen2.5-3B open-domain 7.12 vs 7.04). — [A-MEM](https://arxiv.org/html/2502.12110)
- DuoMem (Jun 2026; procedural task memory, not personal facts): replacing a small student's self-generated memories with teacher-generated memories, plus LoRA, lifted a 4B model on ALFWorld from 4.3% to 77.9% success (72B teacher: 87.1%). — [DuoMem, arXiv 2606.29961](https://arxiv.org/abs/2606.29961)

### Inferences
- Maya's junk ("The user lives in testing", "The user likes no I don't see") matches the mem0/gemma2:2b audit and the Persona-NLI finding. A small extractor asked to produce facts will produce *something* from every input, including fragments, test phrases, negations and questions. The fix must be a gate the extractor cannot talk its way past, not just a better prompt.
- Cheap gates that fit on a phone:
  1. **Source gate:** only extract from user turns, and never from assistant turns, tool output or recalled memory text. This is the #1 fix in the mem0 audit; Maya's background "learn from my chats" must strip MemoryBook lines that were injected into context.
  2. **Span/quote gate:** require a verbatim user quote, and reject a candidate whose content words are not mostly in the quote (Maya's CONFIRMED rule already does this for the remember tool).
  3. **Form gate:** a deterministic check rejecting questions (ends with "?", starts with an interrogative), negations/declines ("no", "I don't"), hypotheticals ("if", "would", "imagine"), reported speech, and fragments under N content words.
  4. **Entailment check:** an NLI cross-encoder of DeBERTa-v3-base size (~184M parameters) is plausible on-device. A weaker proxy is EmbeddingGemma cosine between the candidate fact and its source sentence.
- HaluMem's omission finding (recall < 60%, update omission > 50%) means that tightening gates trades junk for misses. Maya's old keyword-gated remember tool was a pure recall failure, so the design needs a measured operating point (precision and recall on a labelled set), not just stricter filters.
- Memory-R1 shows a 3B to 8B memory manager improves a lot with tiny RL data (152 QA). Fine-tuning Hanu on ADD/NOOP/LINK decisions from a few hundred labelled cases is plausible, but this is evidence for 3B+, not 2B 4-bit.

### Gaps
- I found no paper that specifically counts hypotheticals, jokes or questions mistaken for facts (as separate error classes) in LLM memory extraction. HaluMem's "false memory resistance" (distractor resistance) is the closest measure.
- I found no published precision/recall for a ~2B model doing personal-fact extraction other than the anecdotal mem0 audit (gemma2:2b) and A-MEM's end-task QA scores.
- I did not verify the 89.6% frontier-model junk figure in the primary issue text.

## Q3. How should conflicting or changed facts (name changed, moved city) be handled: overwrite, keep history with validity intervals, or ask the user? What do benchmarks say?

### Takeaway
The evidence favours **keeping history and marking old facts invalid with timestamps** over overwriting or deleting. Zep/Graphiti do this by design. Mem0 switched to it in 2026 and reports its knowledge-update score rising from 79.5 to 93.6 (vendor-measured). Independent benchmarks show every memory system is bad at "selective forgetting": Mem0 scored 18%, Zep 7% and MemGPT 28% on single-hop fact updates in MemoryAgentBench, worse than plain BM25 at 48%. Untrained LLM managers also wrongly treat additions as contradictions. Contradiction should be declared only on explicit evidence, mainly for single-valued attributes. I found no benchmark evidence on asking the user.

### Cited Findings
- Zep invalidates the old edge (t_invalid = new edge's t_valid) and keeps it, so both current state and history survive. — [Zep paper](https://arxiv.org/html/2501.13956)
- Graphiti's rule: contradiction only when the facts "cannot both be true" and there is "explicit evidence that the old fact stopped being true or was replaced"; never "from recency alone". — [graphiti dedupe_edges.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/prompts/dedupe_edges.py)
- Mem0g marks obsolete relationships invalid rather than deleting them. Mem0g beat Mem0 on LoCoMo temporal J (58.13 vs 55.51). — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Mem0 V3 keeps both "lives in New York" and "lives in San Francisco" with temporal context and lets retrieval rank the current one higher. — [Mem0 migration doc](https://docs.mem0.ai/migration/platform-v2-to-v3)
- Vendor-reported LongMemEval after the switch to add-only (April 2026): knowledge-update 79.5 → 93.6; temporal reasoning 51.1 → 97.0; overall 67.8 → 94.4. LoCoMo temporal 63.2 → 92.5. These are platform numbers that the authors say OSS users won't match exactly, and they bundle several changes (entity linking, fused retrieval). — [Mem0 blog](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm). The docs give slightly different headline numbers (LoCoMo 91.6, LongMemEval 93.4). — [Mem0 migration doc](https://docs.mem0.ai/migration/platform-v2-to-v3)
- Zep on LongMemEval knowledge-update: 74.4% vs full-context 76.9% with gpt-4o-mini (a 3.36% drop), and 83.3% vs 78.2% with gpt-4o. — [Zep paper](https://arxiv.org/html/2501.13956)
- **MemoryAgentBench (Jul 2025), FactConsolidation** (counterfactual edits: the newer fact contradicts an older one; agents told newer facts have larger serial numbers), single-hop / multi-hop accuracy: GPT-4o long context 60/5; GPT-5-mini 78/28; BM25 48/3; HippoRAG-v2 54/5; MemGPT 28/3; Cognee 28/3; Mem0 18/2; MIRIX 14/2; **Zep 7/3**. "All methods fail on the multi-hop situation (with achieving at most 28% accuracy)." Reasoning models help on short contexts (o4-mini FC-SH 100 at 6K, 61 at 32K). — [MemoryAgentBench, arXiv 2507.05257](https://arxiv.org/html/2507.05257)
- Memory-R1's motivating case: a user adopts a second dog. The untrained manager "misinterpreted the second adoption as a contradiction" and issued DELETEs plus an ADD. The RL-trained manager did one UPDATE that merged the two. — [Memory-R1](https://arxiv.org/html/2508.19828v4)
- Mem0's v1 update prompt DELETEs a memory on contradiction (e.g. "Dislikes cheese pizza" deletes "Loves cheese pizza"). — [mem0 prompts.py](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py). A practitioner write-up argues this text-similarity-driven resolution can silently delete a memory that should coexist in another context (an opinion piece). — [DEV Community post](https://dev.to/mukesh_13/mem0-auto-resolves-memory-conflicts-for-you-until-it-silently-deletes-one-you-still-need-4f4m)
- ChatGPT memory "tended to overwrite crucial information as the chat continues" in LongMemEval's tests. — [LongMemEval](https://arxiv.org/html/2410.10813)
- LangMem "profiles" (one current-state document updated in place) are its pattern for single-valued state; "collections" handle accumulating facts. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- In the Mem0 paper, OpenAI memory scored very low on LoCoMo temporal questions (J 21.71), "mainly because most generated memories lacked timestamps". LangMem also scored 23.43. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- LoCoMo: LLMs "face challenges in understanding time concepts within dialogues". Human temporal F1 is 92.6 vs 17.5 for GPT-3.5-turbo without retrieval. — [LoCoMo, arXiv 2402.17753](https://arxiv.org/html/2402.17753)

### Inferences
- **Recommended policy for Maya:**
  1. **Every line gets a written-at timestamp, and a valid-from where it differs.** Missing timestamps were the stated cause of OpenAI memory's 21.71 temporal score.
  2. **Never delete on conflict; supersede.** Set `superseded_by`/`valid_to` on the old line and keep it out of the default context. This is the Zep/Graphiti/Mem0-V3 consensus.
  3. **Declare conflict only for single-valued slots** (name, home city, employer, partner, phone number), using a small fixed schema. Multi-valued facts (likes, allergies, pets) are appended. This avoids the Memory-R1 "second dog = contradiction" error and does not need a 2B model to judge "cannot both be true", a judgement MemoryAgentBench shows even GPT-4o fails on.
- **"Victor" vs "Vijay":** two values in an identity slot. In a voice-first app the cause may be an ASR mishearing rather than a real change. Identity slots are rare and high-stakes, so asking the user once ("Should I call you Vijay or Victor?") is cheap and resolves it. For low-stakes slots, newest CONFIRMED value wins with history kept. This is design reasoning; no benchmark tests asking the user.
- A rule of CONFIRMED beats TENTATIVE, and newer CONFIRMED beats older CONFIRMED, can be applied deterministically from Maya's existing status field without any model call.

### Gaps
- I found no benchmark or paper measuring "ask the user to resolve the conflict" against automatic resolution.
- I could not separate how much of Mem0's knowledge-update gain comes from add-only versus the new retrieval stack; no ablation was published.
- MemoryAgentBench's conflicts are synthetic counterfactual edits with serial numbers, not natural "I moved" statements.

## Q4. For a small on-device model, is it better to let it extract memories itself, use deterministic/rule-based extraction plus user confirmation, or use structured triples vs free-text sentences?

### Takeaway
The evidence leans against letting a ~2B model freely extract and rewrite memories. It produced the worst documented junk rates, and even 3B to 8B managers need RL training to make reliable UPDATE/DELETE calls. The safer split is: the user's explicit statements (or the model's tool call) proposing a fact; deterministic gates and dedupe checking it; the verbatim quote kept as the stored value. Short "observation" sentences beat summaries and raw dialogue in LoCoMo. Graph triples gave only small temporal gains at about 2× the cost in Mem0's comparison. Either way, keeping the raw source text with the extracted fact beats storing the fact alone.

### Cited Findings
- **Granularity:** in LongMemEval, replacing sessions/rounds with extracted summaries or facts "generally hurts QA because of information loss". Facts help only on multi-session reasoning. The best design is K = V + fact: index the raw round/session by its extracted facts but keep the raw text. Session: recall@5 0.706 → 0.732, QA 0.670 → 0.714. Round: 0.582 → 0.644, QA 0.615 → 0.657. Average +9.4% recall, +5.4% accuracy. Facts alone as keys did not help (recall@5 0.642 vs 0.706). — [LongMemEval](https://arxiv.org/html/2410.10813)
- **Observations vs summaries vs dialog** (LoCoMo, GPT-3.5-turbo-16k RAG): temporal F1 was 41.9 (top-5 observations) vs 21.3 (top-5 dialog) vs 31.0 (top-5 summaries). Overall F1 was 41.4 / 31.7 / 32.5. Summaries lose information. — [LoCoMo](https://arxiv.org/html/2402.17753)
- **Triples vs sentences:** Mem0g (graph triples) vs Mem0 (sentences), LoCoMo J: single-hop 65.71 vs 67.13, multi-hop 47.19 vs 51.15, open-domain 75.71 vs 72.93, temporal 58.13 vs 55.51. Overall 68.44 vs 66.88. Tokens 3,616 vs 1,764; search p50 0.476 s vs 0.148 s. Storage about 14k vs 7k tokens per conversation; Zep > 600k. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Mem0 V3 replaced its graph store with entity extraction (proper nouns, quoted text, compound noun phrases) into a lookup layer that boosts ranking, keeping memories as sentences. — [Mem0 migration doc](https://docs.mem0.ai/migration/platform-v2-to-v3)
- **Model-only extraction at 2B:** the mem0 audit (gemma2:2b for 20 of 32 days) found hallucinated profiles, identity confusion, wrong locations and fabricated lifestyle entries, plus the self-reinforcing "User prefers Vim" loop. — [mem0 issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- **Trained small managers:** Memory-R1 shows 3B to 14B managers need RL fine-tuning (152 QA) to beat in-context baselines. Base Qwen-2.5-3B pipeline J is 41.24 vs 57.92 after GRPO. — [Memory-R1](https://arxiv.org/html/2508.19828v4). Mem-α (Sep 2025) argues LMs "lack the ability to determine which information to store, how to structure it, and when to update it". It trains memory construction with RL (rewards from downstream QA plus format/compression/content-quality terms), trained on ≤30k-token instances and generalising to >400k. — [Mem-α, arXiv 2509.25911](https://arxiv.org/html/2509.25911v1)
- **Small classical extractors:** persona triple extraction from dialogue has a long non-LLM line of work. DialogNLI annotates PersonaChat utterances with (subject, relation, object) triples; PAED (ACL 2023) is a zero-shot BART extractor. Without negatives these extractors over-generate, and an NLI filter is needed. — [Extracting and Inferring Personal Attributes from Dialogue, arXiv 2109.12702](https://arxiv.org/pdf/2109.12702); [Persona-NLI, arXiv 2401.06742](https://arxiv.org/html/2401.06742v1)
- **Self-directed writing needs function-calling skill:** MemGPT degraded with GPT-3.5 "due to limited function-calling ability". — [MemGPT](https://ar5iv.labs.arxiv.org/html/2310.08560)
- **Under-recording is the other failure:** Coze "often failed to record indirectly provided user information". — [LongMemEval](https://arxiv.org/html/2410.10813)
- **Small-model temporal extraction is unreliable:** Llama 3.1 8B "often hallucinat[es] or miss[es] temporal cues". — [LongMemEval](https://arxiv.org/html/2410.10813)

### Inferences
- **Recommended split for Maya (2B planner + EmbeddingGemma):**
  - (a) **Foreground, explicit:** when the user states a first-person fact ("I have a peanut allergy", "my daughter is Asha", "I moved to Pune"), Hanu may call `remember`, which must carry a verbatim user quote. Deterministic code then validates and normalises it. The remember tool must be always available, not keyword-gated. Keyword gating caused the peanut-allergy miss, matching the Coze "failed to record" failure.
  - (b) **Background "learn from chats":** demote to *proposals only*. Run deterministic candidate detection (first-person declaratives about stable attributes: "I am / I have / I live / my X is / I'm allergic / I prefer"), then Hanu (or no model) phrases a sentence, then gates (Q2), then store as TENTATIVE, invisible to planning until confirmed or seen twice. Never extract from assistant turns or recalled memory lines.
  - (c) **Dates:** convert relative dates with a deterministic date parser, not the 2B model, given Llama-8B's measured temporal-cue failures.
- **Representation:** keep short sentences as the main unit. Observations beat summaries; graph triples cost about 2× for small gains. Add a few typed slot fields for single-valued attributes, and always keep the verbatim quote (Maya's CONFIRMED proof) as the "value", per LongMemEval K = V + fact. A full knowledge graph (Zep-style, > 600k tokens storage and many LLM calls per write) does not fit a 2B phone budget.
- If Hanu is to keep doing background extraction, Memory-R1/Mem-α suggest fine-tuning it on a small labelled set of ADD / NOOP / LINK / REJECT decisions rather than relying on prompting. A REJECT label was proposed in the mem0 audit.

### Gaps
- I found no head-to-head study of rule-based vs LLM extraction for personal assistant memory on the same data with precision/recall.
- I found no study of user-confirmation UX (confirm prompts vs silent save) measuring accuracy or user burden.
- I did not fetch PAED or DialogNLI full results; their numbers are not included.

## Q5. What safeguards against destructive consolidation do systems use (undo logs, never deleting user-authored facts, rate limits)?

### Takeaway
Serious systems now treat deletion as the exception. They append and invalidate instead of overwriting (Zep, Mem0 V3, Mem0g), keep raw episodes as a non-lossy source (Zep), turn deletes off by default (LangMem), back up or version memory before reorganising (Letta MemFS git commits, backup before merge/split), add review passes (Letta "Agent reviews before applying"), and debounce background work. I found no published per-pass edit cap like nanoMuse's "at most 1/5 of the store", and no published "merged line adds no new words" check; those are nanoMuse-specific.

### Cited Findings
- Letta: "The memory workflow backs up the current repository before splitting large files, merging duplicates". The optional "Agent reviews before applying" pass revises proposed updates in a second background conversation; it "uses more model tokens and does not ask you for approval". — [Letta sleep-time/dreaming docs](https://docs.letta.com/guides/agents/architectures/sleeptime)
- Letta MemFS: memory is a git repository; "Every memory edit is committed to the MemFS git repository. This provides version history, conflict resolution, and a clear boundary between saved memory and uncommitted changes". Background memory subagents (dreaming, "memory doctor") use git worktrees. — [Letta MemFS docs](https://docs.letta.com/concepts/memfs)
- LangMem: `enable_deletes=False` by default in `create_memory_manager`. Background reflection can be delayed (`after_seconds`) to debounce and deduplicate work. — [LangMem API reference](https://langchain-ai.github.io/langmem/reference/memory/)
- Mem0 V3: "ADD only: nothing is overwritten or deleted". Explicit `delete()` remains, with `delete_linked` controlling whether superseded chains go too. — [Mem0 migration doc](https://docs.mem0.ai/migration/platform-v2-to-v3); [Mem0 memory decay blog](https://mem0.ai/blog/introducing-memory-decay-in-mem0)
- Zep keeps raw episodes as a non-lossy source and only invalidates edges, so derived facts can be re-checked against the original text. — [Zep paper](https://arxiv.org/html/2501.13956)
- Generative Agents reflections store pointers to the evidence records they cite, giving provenance for every consolidated insight. — [Generative Agents](https://ar5iv.labs.arxiv.org/html/2304.03442)
- mem0 ships a read-only "memory-reviewer" skill (flags duplicates, contradictions, low-confidence entries) separate from a "dream" consolidation skill (merge duplicates, resolve contradictions, prune stale entries). This separates audit from mutation. — [mem0 memory-reviewer skill listing](https://www.skills.sh/mem0ai/mem0/memory-reviewer)
- The mem0 audit's proposed safeguards: feedback-loop prevention (tag recalled memories), a quality gate before storage, and a REJECT action. — [mem0 issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- A-MEM's "memory evolution" rewrites neighbouring notes in place with no history described, which is a counter-example with no safeguard. — [A-MEM](https://arxiv.org/html/2502.12110)
- MemoryOS evicts the lowest-heat segment when capacity is exceeded and caps persona stores as 100-entry FIFOs, so it does delete, by a deterministic rule rather than an LLM. — [MemoryOS](https://arxiv.org/html/2506.06326)

### Inferences
- **Safeguard set for Maya (all deterministic, phone-friendly):**
  1. Append-only journal / undo log of every MemoryBook mutation (like MemFS commits).
  2. Supersede instead of delete. Only the user's explicit "forget X" hard-deletes.
  3. Never auto-delete or auto-rewrite CONFIRMED (user-quoted) lines. Background passes may only merge exact or near duplicates (Jaccard ≥ 0.9, or a calibrated EmbeddingGemma cosine) into the older line and keep the quote.
  4. Merges must not add new content words (nanoMuse's check; no published equivalent found, but it is a cheap guard against 2B hallucination during merge).
  5. Cap edits per pass (nanoMuse's 1/5) and run tidy-up only after N new lines or weekly, with debounce (as in LangMem).
  6. Expire TENTATIVE lines that are never confirmed or re-observed within a window. This is MemoryBank-style decay applied as deletion only to unconfirmed guesses.
- nanoMuse's design (dedupe-or-replace at ≥ 0.8, `replaces` id, periodic tidy-up with undo log and never dropping user-written lines) matches the safest published patterns. Its main risky piece for a 2B model is "keep the newer of conflicting facts" decided by the model. The Graphiti "explicit evidence only" rule plus slot-typed conflicts (Q3) addresses that.

### Gaps
- I found no published numbers on how often LLM-driven consolidation destroys correct memories (an "erroneous delete rate"), beyond Mem0's qualitative admission and Memory-R1's single example.
- I found no system documenting a per-pass edit cap or a "merged text must not add words" validator. These appear to be nanoMuse-specific.
- OpenAI's ChatGPT memory pages (FAQ and launch post) returned HTTP 403, so its user controls (memory-updated notices, manage/forget, sensitive-data handling) are not cited here.

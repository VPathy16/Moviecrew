# R1 Prompt & context engineer: position on agenda item 2

Paths relative to app/src/main/java/com/mealmate/app/. Industry claims are from public context-engineering guidance (smallest high-signal context, stable prefix, just-in-time retrieval); how they apply here is my inference.

## Verdict
The app is already better than most: system prompt is pinned by hash (UserTurn.kt:103-112), static, name-only substitution (LocalBrain.kt:237); per-turn text is a fixed-order contract (UserTurn.kt:27-43); the prefix is warmed (LocalBrain.kt:216) giving 1,240 reused tokens. Menu routing with sensitive-word full-menu and no_tool retry (UserTurn.kt:69-95, PlanRunner.kt:72-75) is the right just-in-time pattern. The remaining risk is not the format but everything that lives *outside* what the model was trained on.

## Train/serve skew still open (measured against the DPO file, 999 rows)
- **Every DPO prompt is exactly [system, user]**, no history. The app sends the last 2 request/plan pairs as extra turns (Turns.kt:110 `PLANS = 2`, TurnEngine.kt:79, GemmaTurns.kt:23). The model has never seen a prior turn in this role layout. Worse, stored plans are `SecretFilter.mask`ed (TurnEngine.kt:81), so masked tokens appear in model-role turns it never produced. The 19/20 replay and 17/20 ask-before-speak numbers were probably measured without this, so they don't cover production input.
- **`(nothing saved about this)`** (LocalAssistant.kt:115) appears 0 times in DPO and is not in APP_TURN_FORMAT.md. It is an invented note on exactly the privacy-sensitive path (MEMORY NOTES).
- **Menu shape**: only 11/999 DPO rows have TOOLS, and then 2-7 items. The app emits 3-5 of 10 hand-ranked items; the item set (Connectors.kt:15-28) is a subset of CONNECTOR_LIST_v4 and drops mail/consent connectors that trained menus always mix in as distractors. Distribution shift is likely; an eval can tell.
- **Memory volume**: DPO notes average 2.7, max 5. App sends core + found with no visible cap (LocalAssistant.kt:115). Many notes dilute the "answer only the exact fact" behaviour.
- The legacy v2 path inlines `MEMORY NOTES: a b c` (TurnEngine.kt:74), a different format; fine only because it is gated by `v027`.
- `{name}` is one of 7+ values in training, so the cached prefix differs per name; fine, but the pin hash is of the template, not what is sent. Pin the rendered text too.

## Ranked changes

1. **Make serve-time input byte-identical to a trained distribution: drop or re-train history (S to drop, M to retrain).** Default to single-turn (matches training); carry follow-up context via code (Pending/YesNo already do yes/no). If follow-ups matter ("make it 6pm"), have the team add multi-turn rows and show history as one compact `PREVIOUS: <request> -> <plan summary>` line only after it is trained. Impact: high; removes the largest unmeasured skew.
2. **Golden-prompt contract test (S).** Render UserTurn.build + GemmaTurns.prompt for N recorded cases and diff against the training team's exact rendered strings (incl. chat-template tokens `<|turn>`, GemmaTurns.kt:14-24, which the training framework's template must match byte for byte). Put the sha of the *rendered* system prompt and a template-version in every turn trace. Impact: high, catches silent drift.
3. **Remove untrained strings (S).** Replace `(nothing saved about this)` with either omitting the block or a trained form; ask the team which. Audit any other literal reaching the model (RESULT/SCREEN text, route fallback UserTurn.kt:36). Impact: medium-high on privacy.
4. **Cap and rank memory notes (S/M).** Max 5 notes, short, relevance-ordered, secret-filtered (already UserTurn.kt:28); only core facts relevant to the request, not all "always-known". The margin gate (LocalAssistant.kt:110-114) is good just-in-time retrieval; add top-k. Impact: medium.
5. **Menu design: distractor-aware routing (M).** Keep top-k but always include one or two near-miss siblings (alarm vs timer vs schedule) and the consent/mail items once they exist; evaluate recall of the right tool at k=3/5/full on a labelled set rather than regex ranking (Connectors.kt:15-34 is brittle: `\d` makes calc generic for any digit). Log router recall and no_tool-retry rate; each retry costs a full re-read (PlanRunner.kt:74). Impact: medium; also latency.
6. **KV-cache hygiene (M).** Today the cached prefix is system only; with history the second block slides every turn. After dropping history, the prefix can extend to system + stable MEMORY NOTES/USER... but order is fixed by training (notes first, so a changing question follows). Keep it simple: cache system only, avoid re-warming with a different ending, and make the retry reuse the prefix up to TOOLS (it differs only on the TOOLS line, so put no content after it that varies). Saved prompt KV to disk (on the future list) turns the 16 s cold read into a load: do it (M). Impact: latency, not accuracy.
7. **Few-shot vs fine-tune: fine-tune only (decision).** The 1,250-token prompt already spends budget; do not add few-shot examples to the app (breaks pin and training match). Fix behaviours via DPO/SFT rows plus code guards. For the 3/20 speaker-leak gap, a code backstop (not more prompt text) is the right fix. Impact: medium.
8. **Version everything as one bundle (S).** Model sha + system prompt sha + GBNF sha + turn-format version + ToolMenu/Connector list version in one manifest, written to each TurnTrace and refused on mismatch (PromptManifest covers prompt only; grammar and connector list are unpinned). Impact: medium.

## What I expect other specialists to get wrong
The architect will want RESULT re-plan turns and richer multi-turn state; the evals person will measure on the DPO prompts (which are single-turn and menu-light). Both will validate a model on inputs production never sends. The on-device person will propose trimming the system prompt to save the 16 s cold read; that breaks the training match and fails silently, whereas a disk KV snapshot does the same job safely.
